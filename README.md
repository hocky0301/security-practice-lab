# security-practice-lab

AIに作業を任せるとき、「承認した」「検査を通した」「ログに残した」「センサーが動いている」は、それぞれ何を保証しているのか。どこまでが保証で、どこからが思い込みなのか。私はそこが曖昧なまま運用に入ると事故が起きると考えて、小さな実験にして確かめました。

このリポジトリは、その実験コードです。ローカルで動く小さな実験コードで、公開・依存と道具・認可と予算・記憶と復旧・観測の5つの場面について、「この検査が通っても、まだ言えないこと」を単体テストと保存済みの結果で示します。

## 確かめていること

- 署名が正しいファイルでも、公開してよいとは限らない。ファイルの中身、作った工程、公開先を別々に照合すると何が変わるか。
- 依存パッケージの一覧が同じでも、AIが使う道具の説明文や権限だけが変わることがある。変更を見つけ、許可されていない操作を止められるか。
- 1回ごとの許可は範囲内でも、100回続けると予算を超える。合計の枠と有効期限をどう持つか。
- 「前に承認した」という記憶や要約を、今の許可として扱わない。取り消した承認を、復旧の過程で復活させない。
- 画面の更新時刻と、実際に測った時刻は別物。表示が新しくても、観測が古いことを見分けられるか。

## 確かめていないこと

外部のシステムへの攻撃ツールではありません。ネットワーク、本物のLLM、実機、本物の署名・認証の仕組みには一切つながっていません。ここにある結果は、すべて合成した入力から作ったもので、実際の運用で測った数字ではありません。通るテストの数は、守れる範囲の広さや安全性の点数ではありません。

## 動かす

標準ライブラリだけで動きます。Python 3.10以降が必要です。公開用ファイルの書き出しの試験にはPOSIXの機能を使うため、未対応の環境では成功扱いにしません。

```bash
python -m unittest discover -s tests -v
python verify_reproduction.py
```

`verify_reproduction.py` は、テストを全部走らせたうえで、合成実験をもう一度計算し、`results/` に保存してある2つの結果と構造が一致するかを確かめます。実行の記録は `verification_report.json` に書かれます（このファイルは Git には入れていません）。

結果を別の場所へ出し直すには、次のようにします。

```bash
python -m security_lab.experiments --out results-original-local
python -m security_lab.frontier_experiments --out results-frontier-local
```

新しい場所にクローンして、最初から通るか確かめるには `scripts/verify_fresh_clone.sh` を使います。一時ディレクトリへクローンし、新しい仮想環境へ `pip install -e .` して、テストと `verify_reproduction.py` を走らせ、どれかが失敗すれば異常終了します。取得元は環境変数 `REPO_URL` で指定します（省略すると、いま手元にあるこのリポジトリを使います）。

```bash
REPO_URL=https://github.com/hocky0301/security-practice-lab.git scripts/verify_fresh_clone.sh
```

## 手で試す

`demos/green_room.html` をブラウザで開きます。観測だけを止めて1秒進めると、「描画の古さ0ms」と「実測の古さ1000ms」が同時に出ます。実カメラも監視用のAIも使っていません。

## 各モジュールが答える問い

| 場面 | モジュール | 答える問い |
|---|---|---|
| 公開 | `release.py` | レビューしたバイト列だけを書き出せるか。作業ツリーやGit履歴を持ち出さないか |
| 公開 | `release_context.py` | 同じファイルでも、作った工程や公開先が承認と違うとき止められるか |
| 依存・道具 | `dependencies.py` | 検査の結果が揃っているか。期限つきの例外が切れたら通らなくなるか |
| 依存・道具 | `tool_contracts.py` | 道具の定義が変わったことを見つけ、許可していない操作を止められるか |
| 認可 | `authority.py` | 内容に結びついた1回限りの承認、世代、再送、結果が分からない場合の扱い |
| 認可 | `capability_budget.py` | 共有の合計枠を、同時に来た要求の間で超えずに配れるか |
| 記憶・復旧 | `memory_authority.py` | 取り消した承認が、要約や記憶から許可として戻ってこないか |
| 記憶・復旧 | `audit.py` | 出来事の記録がつながっているか（記録が真実かどうかは別問題） |
| 記憶・復旧 | `recovery.py` | データは戻しても、古い権限は戻さずに復旧できるか |
| 観測 | `observations.py` | 観測データに、出どころ・種類・時計・順序が揃っているか |
| 観測 | `evidence_age.py` | 実測・予測・描画の時刻を混ぜずに、古い証拠を見分けられるか |
| 実験 | `experiments.py`, `frontier_experiments.py` | 上のモジュールで合成した場面を走らせ、`results/` に保存する |

分野ごとの対応は [docs/TOPIC_MAP.md](docs/TOPIC_MAP.md)、前提と限界は [脅威モデル](docs/THREAT_MODEL.md)、追加実験の読み方は [docs/FRONTIER_EXPERIMENTS_JA.md](docs/FRONTIER_EXPERIMENTS_JA.md)、確認できたこととできていないことは [docs/EVIDENCE.md](docs/EVIDENCE.md) にあります。

## 限界

- ネットワークには接続しません。外部APIを呼ぶ処理も、外へ出す通信の制限も実装していません。
- 本物のLLMは呼びません。「AIの要約がどれだけ誤るか」は測っていません。
- 本物の署名の生成・検証、認証、鍵の管理はありません。署名の検証が終わった後の入力を、呼び出し側が正しく渡すと仮定しています。
- 予算の台帳が保証するのは、1つのSQLiteの中の模擬的な効果だけです。外部のAPIを含めた「ちょうど1回」の実行、課金の返金、実機の非常停止は実装していません。台帳を複製して別々に持てば、合計の保証は成り立ちません。
- 信頼する側の記録（現在の台帳、最新の位置を示す値、時計）を書き換えられる相手には、この模型は役に立ちません。その場合の反例もテストに残しています。
- 各モジュールは1つにつながったシステムではありません。時計の単位や鮮度の上限は、モジュールごとに別の設定です。つなぐなら、単位と基準の時計を先に決める必要があります。
- 脆弱性のスキャナーではありません。スキャナーの出力を正規化した後の判断だけを扱います。

## CIとDependabot

`.github/workflows/ci.yml` と `.github/dependabot.yml` は、私がこのリポジトリで実際に使う設定です。

- CI：プルリクエストと `main` への push で、Python 3.10、3.11、3.12 それぞれについて、単体テストと `verify_reproduction.py` を走らせます。権限は `contents: read` だけで、チェックアウト時に認証情報を残しません。使うActionは完全なコミットSHAで固定しています。
- Dependabot：GitHub Actionsのバージョンだけを、週に1回確認します。このリポジトリは外部の依存パッケージを持ちません。

これらはGitHubに公開してから動き始めました。公開した直後（2026-10-11）に、main への push で CI が1回走り、Python 3.10・3.11・3.12 とも通りました（[実行の記録](https://github.com/hocky0301/security-practice-lab/actions/runs/38110268802)）。同じ時刻に Dependabot が、Actions の版を上げる提案を2件出しました（[#1](https://github.com/hocky0301/security-practice-lab/pull/1)・[#2](https://github.com/hocky0301/security-practice-lab/pull/2)。どちらも大きい版の更新で、取り込むかは検討中です）。結果はリポジトリの Actions タブで見られます。手元では、Python 3.10、3.11、3.12 で同じ2つの確認を実行しました。
